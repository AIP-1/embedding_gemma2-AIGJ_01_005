# Jetson 엣지 AI 실습 결과 보고서 (1~10단계)

2026-11-03 · 김채림

## 개요

팀 공용 Jetson에서 GPU 기반 임베딩 모델을 실행하고, 성능 측정, 도메인 미세조정, 물체 검색, 사람 동작·행동 인식, 카메라 2대 접근 감지까지 1~10단계 실습을 수행했다. 각 단계의 측정 결과와 원인 분석을 정리한다.

| 항목 | 내용 |
| --- | --- |
| 장비 | Jetson (8GB 메모리, NVMe SSD로 부팅) |
| 소프트웨어 | JetPack 7.2.1 (Jetson Linux R39.2.1), Ubuntu 24.04, CUDA 13.2, Python 3.12.3 |
| 접속 | Mac → Tailscale → `ssh team2@<보드 주소>`, 웹 화면은 `http://<보드 주소>:8000` |
| 계정 | 메인 계정 team2에 설치 (개인 계정은 t2) |
| 작업 폴더 | `~/eg2-lab`, 가상환경 `~/eg2` |
| 카메라 | USB 웹캠 1대 (`/dev/video0`) |

접속할 때마다 처음에 하는 두 줄:

```
cd ~/eg2-lab && source ~/eg2/bin/activate
```

## 1~5단계 환경 준비

GPU용 PyTorch가 `+cu132`로 설치되고 실제 GPU 계산까지 성공해서 환경 준비가 끝났다. 자료는 JetPack 6 기준이었지만, 이 Jetson은 JetPack 7.2.1이라 설치 방법을 바꿨다.

| 단계 | 한 일 | 결과 |
| --- | --- | --- |
| 0. SSD | `lsblk`로 확인 | 이미 SSD로 부팅 중이라 건너뜀 (실수로 만든 `/ssd` 중복 마운트는 되돌림) |
| 1. 버전 확인 | `cat /etc/nv_tegra_release` | R39 = JetPack 7. `nvcc`는 없지만 torch 실행에는 필요 없음 |
| 2. 성능 모드 | `nvpmodel -m` + `jetson_clocks` | 0번은 15W였음 → 목록에서 MAXN\_SUPER 번호를 찾아 적용 |
| 3. 스왑 | `/swapfile` 8GB | `free -h`에서 스왑 8.0Gi 확인 |
| 4. 가상환경 | `python3 -m venv ~/eg2` | 시스템 파이썬과 분리, team2 계정에만 설치 |
| 5. PyTorch | `pip install --pre torch torchvision --extra-index-url https://download.pytorch.org/whl/cu132` | `+cu132`, `(8, 7)`, GPU 행렬 계산 성공 |

참고 사항:

- 가상환경으로 시스템 파이썬과 분리해, 다른 계정과 상시 실행 중인 프로그램에 영향을 주지 않도록 했다.
- `+cu132`는 CUDA 13.2용 빌드를 뜻한다. `is_available()` 외에 실제 GPU 행렬 연산으로 동작을 검증했다.
- 실행 시 출력되는 CC 8.7 경고는 NVIDIA 안내에 따라 무해한 경고로 판단했다.
- 이후 패키지 설치 시 `-c ~/torch-lock.txt`로 torch 버전을 고정해 덮어쓰기를 막았다.

## 6단계 성능 측정

텍스트·비전·오디오를 모두 올린 전체 구성도 8GB Jetson에서 메모리 부족 없이 돌아갔다. 가장 무거운 전체 구성의 로드 후 RAM은 약 5,929MB였다.

| 구성 | 로드 크기 | 로드 후 RAM (MB) | 입력 | 지연 (ms) | GPU 사용률 (%) |
| --- | --- | --- | --- | --- | --- |
| 텍스트 전용 | 270M | 약 4,670 | 질의 2개 | 158 | 약 4 |
| +비전 | 440M | 약 5,463 | 이미지 5장 | 2,645 | 99 |
| +비전 | 440M | 약 5,463 | 동영상 10초 | 2,020 | 99 |
| +오디오 | 570M | 약 5,029 | WAV 2개 | 1,262 | 약 19~32 |
| 전체 | 740M | 약 5,929 | 혼합 | 6,000 | 99 |

측정 조건: MAXN\_SUPER + `jetson_clocks`, 스왑 8GB, 지연은 두 번째 실행 값.

비고:

- **로드 후 RAM**은 `python -i`로 모델을 띄워 둔 `>>>` 상태에서 tegrastats로 읽었다. 아무것도 안 돌릴 때도 약 3,100~3,300MB를 쓰므로(팀원 프로그램, 화면 등) 모델이 실제로 차지한 양은 텍스트 약 1.4GB, 전체 약 2.7GB다.
- \*\*텍스트 GPU 약 4%\*\*는 처리가 0.15초로 너무 짧아 0.1초 간격 측정에 순간만 잡힌 값이다.
- **오디오**는 WAV가 2개라 표 조건(3개)과 다르다.
- **전체 지연 6,000ms**에는 처음 실행되는 텍스트의 준비 시간(642ms, 단독일 때는 158ms)이 섞여 있다.
- 로드 크기는 오디오가 더 큰데 RAM은 비전이 더 높았다. 영상 해독과 이미지 처리에 추가 메모리를 쓰기 때문으로 보인다.

## 7단계 도메인 미세조정

강의실 데이터로 약 64초 학습하자 accuracy@1이 0.85에서 0.9로 올랐다. 평가 질문 20개 중 1등으로 정답을 찾은 개수가 17개에서 18개로 늘었다는 뜻이다.

| 모델 | accuracy@1 | accuracy@3 | ndcg@10 | 학습 시간 |
| --- | --- | --- | --- | --- |
| 기준 (google/embeddinggemma-2) | 0.85 | 1.0 | 0.938 | - |
| 미세 조정 (eg2-classroom) | 0.9 | 1.0 | 0.95 | 약 64초 (63.98초) |

**데이터**: 강의실 환경 문서 20개(환기·CO2, 냉난방, 습도, 조명, 소음, 미세먼지, 센서, 안전 등)마다 질문 4개를 만들어 3개는 학습용(`train.jsonl` 60줄), 1개는 평가용(`eval.jsonl` 20줄)으로 나눴다. 평가 질문은 학습 때 본 적 없는 표현이다.

**학습 과정**: loss가 3.077 → 3.938 → 2.81 → 2.242 → 2.439 → 2.008로 오르내리며 전체적으로 줄었다. 데이터가 60줄로 작아서 흔들림이 있었다.

**해석**:

- accuracy@3은 학습 전에도 1.0이라 정답이 항상 3위 안에 있었다. 그래서 효과는 accuracy@1과 ndcg@10(정답을 더 위쪽에 놓는 정도)에서 보였다.
- 기준 모델은 Google이 이미 학습한 모델을 받아 쓴 것이라 학습 시간이 없다.
- 데이터가 작아서 향상 폭도 작다. 데이터를 늘리면 차이가 더 분명해질 수 있다.

## 8단계 물체 검색 (yolo / relabel / yoloe)

YOLO가 모르는 물체 3개(세탁기, 전지 포장, 건전지)를 yolo는 하나도 못 맞혔고, relabel이 가장 많이(3개) 바로잡았다. 세 방식의 속도와 메모리는 큰 차이가 없었다.

세 방식의 차이:

- **yolo**: YOLO가 배운 80종 중 하나를 반드시 고른다. 모르는 물체는 비슷한 클래스로 틀린다.
- **relabel**: YOLO 박스는 그대로 쓰고, 잘라 낸 사진을 임베딩해서 LABELS 목록 중 가장 비슷한 이름을 다시 붙인다.
- **yoloe**: 처음부터 LABELS의 영어 이름을 찾을 대상으로 지정해서 검출한다.

| --- | --- | --- | --- |
| yolo | 16.7 | 594 | 약 5,700 |
| relabel | 14.4~17.0 | 581~614 | 약 6,026 |
| yoloe | 15.0 | 630 | 약 5,842 |

비고:

- 영상 박스 위 숫자는 **YOLO 검출 신뢰도**, relabel 점수는 웹 "최근 추출" 카드의 괄호 속 **임베딩 유사도**다. 둘은 다른 숫자다.
- 검출 fps와 임베딩 ms는 웹 "최근 추출" 줄 값으로 통일했다.
- relabel의 한계: 박스가 안 잡히면 고칠 수 없고, 목록에 없는 물체(충전기 → 물병, 방열판 → 전지 포장)도 억지로 바꾼다. 세탁기처럼 목록 안의 비슷한 짝(전자레인지)과 헷갈리기도 한다.
- yoloe의 한계: 기본 신뢰도 기준(0.25)이 낮아 오검출이 많고(인형 → 마우스 등), 같은 물체도 장면마다 결과가 흔들렸다.

**정리**: 추가 학습 없이 정확도가 가장 높았던 relabel이 강의실 서비스에 적합하다. 다만 헷갈리는 짝(세탁기/전자레인지 등)은 LABELS 문구를 보강해야 한다.

## 9단계 사람 동작·행동 인식

규칙에 시간 정보를 더하자(smooth) 깜빡임이 줄었고, 직접 녹화한 데이터로 GRU 모델을 학습하자 규칙으로 불가능했던 박수·팔짱을 인식했다. 학습 모델은 처음 본 사람에게도 15번 중 13번(87%)을 맞혔다.

관절 찾기는 모두 YOLO11n-pose가 하고, 달라지는 건 **판정 방법**뿐이다.

| 판정 방법 | 방식 | 실행 |
| --- | --- | --- |
| raw (9-1) | 한 프레임만 보고 규칙으로 판정 | `--raw` |
| smooth (9-2) | 0.6초 다수결 + 1.5초 손목 움직임으로 손흔들기 판정 | 옵션 없음 |
| 행동 규칙 (9-5) | 정면 시간·이동 속도로 지나감/힐끗 봄/관심 있음/머무름 판정 | `--behavior` |
| 학습 모델 (9-6) | 녹화 데이터로 학습한 GRU가 약 2초 움직임을 보고 판정 | `--model ...` |

### 9-4 결과 비교 (raw vs smooth)

| 동작 (실제 횟수) | 9-1 raw 카운트 | 9-2 smooth 카운트 | 비고 (오판·미검출) |
| --- | --- | --- | --- |
| 만세 (3회) | 만세 3 | 만세 3 | raw: 팔을 올리고 내릴 때 한팔들기 6번 깜빡임. smooth: 깜빡임 없이 정확 |
| 한팔들기 (3회) | 한팔들기 3 | 한팔들기 3 | raw·smooth 모두 정확 (smooth는 서서 했을 때) |
| 손흔들기 (3회) | 0 | 손흔들기 3 | raw: 모두 한팔들기로 인식. smooth: 흔들기 시작 후 1~1.5초 동안 한팔들기로 나오다가 손흔들기로 바뀜. 두 사람이 겹쳐 있을 때 손흔들기로 오판 |
| 악수 (3회) | 약 5~6 | 악수 5 | 공통: 전신이 보여야 인식되고, 맞잡고 가만히 있으면 손목이 가려져 미검출. raw: 크게 흔들 때 켜졌다 꺼졌다 하며 연속 카운트, 두 사람이 겹치기만 해도 악수로 오인식. smooth: 천천히 흔들어도 3회보다 많이 카운트 |
| 측면에서 만세 (3회) | 만세 6 | 만세 5 | 공통: 완전한 옆모습에서는 반대쪽 어깨가 가려져 미검출. raw: 비스듬할 때만 인식되며 2배로 과다 카운트. smooth: 한쪽 방향으로 돌리면 한팔들기·손흔들기로 오판 |

### 9-5 행동 패턴 (규칙)

| 시나리오 (3회씩) | 기대 패턴 | 맞은 횟수 | 틀린 경우 나온 패턴 |
| --- | --- | --- | --- |
| 그냥 지나감 | 지나감 | 3/3 | 없음 (한 번은 추적이 끊겨 2명으로 기록됐지만 둘 다 지나감) |
| 걸으며 2초 봄 | 힐끗 봄 | 1/3 | 지나감 2회 (2초 봤지만 정면 시간이 1초로만 잡힘) |
| 멈춰서 5초 봄 | 관심 있음 | 3/3 | 없음 (정면 5~6초로 안정적으로 잡힘) |
| 옆을 보며 15초 서 있음 | 머무름 | 0/3 | 힐끗 봄 3회 (옆모습이라 한쪽 어깨가 가려져 멈춘 동안 판정이 갱신되지 않음, 들어올 때 정면 2초가 잡혀 힐끗 봄으로 확정) |

규칙은 **시선이 아니라 머리 방향**을 본다. 걸으면서 고개를 돌리면 완전히 정면이 되는 시간이 짧아 힐끗 봄을 놓쳤다.

### 9-6 학습 결과

| 모델 | 라벨 | 학습 / 검증 조각 | 최고 검증 정확도 | 헷갈린 부분 |
| --- | --- | --- | --- | --- |
| 동작 (action.pt, window 30) | arms\_crossed, clap, idle, wave | 845 / 169 | 0.976 | 팔짱 30개 중 3개를 손흔들기, 1개를 기본으로 오판 |
| 행동 (behavior.pt, window 30, val 0.3) | glance, interested, passing | 648 / 151 | 1.000 | 지나감 검증 조각이 2개뿐이라 지나감 정확도는 참고 수준 |

행동 모델은 다섯 번 고쳐서 만들었다.

1. window 80 → 검증 조각 0으로 학습 불가
2. window 40 → 학습은 됐지만 검증 조각이 힐끗 봄 5개뿐 (100%는 의미 없음)
3. window 30, val 0.3 → 세 라벨 모두 검증 조각 생김, 정확도 0.862
4. 지나감 추가 녹화 → 지나감 학습 조각 21→99, 대신 정확도 0.785 (관심 있음이 지나감으로 많이 헷갈림)
5. 관심 있음을 멈춰서 보는 장면만 다시 녹화 → 관심 있음 학습 124→367, 정확도 1.000

지나감 녹화는 평균 2초짜리 구간 85개로 잘게 끊겨 있었다(50프레임 이상 구간은 4개). 화면이 좁아 빨리 지나가고, 옆모습에서 추적이 자주 끊겼기 때문이다.

| 박수·팔짱 (규칙 없음) | 불가 | 박수: 느리게 3/3, 빠르게 0/3(팔짱으로 오판). 팔짱: 4/4(박수 오판 2회). 비슷한 자세라 서로 헷갈림 |
| 힐끗 봄 / 관심 있음 구분 (9-5 표) | 힐끗 봄 1/3, 관심 있음 3/3 | 관심 있음 3/4(수정 전), 2/2(모델 라벨 한글 변환 후). 힐끗 봄은 glance↔passing이 번갈아 나와 불안정. 지나감은 4회 중 1회 |
| 처음 본 사람에 대한 정확도 | 규칙은 사람마다 학습하지 않아 같은 기준 | 15번 중 13번 (87%): 손흔들기 3/3, 팔짱 3/3, 관심 있음 3/3, 힐끗 봄 3/3, 빠른 박수 1/3 |

비고:

- 모델은 확신이 70% 미만이면 규칙 결과를 대신 보여 준다. 그래서 모델 라벨과 규칙 라벨이 번갈아 섞여 나온다.
- 코드 수정(모델 라벨을 한글로 변환, idle일 땐 규칙 결과 유지) 전에는 요약 줄에 모델 판정이 반영되지 않아, 상태 변화 기록으로 모델 결과를 확인했다.
- 처음 본 사람에게도 87%를 맞혀, 모델이 녹화한 본인에게만 맞춰지지 않았음을 확인했다. 약점은 본인 테스트와 같이 빠른 박수였다.

## 10단계 카메라 2대 접근 감지

교육장의 IP 카메라(VIGI C540-W)에 11월 2일 USB 웹캠(C920)을 더해 카메라 2대로 사람 위치를 구하고, 타겟에 다가가면 알람을 울렸다. 두 카메라로 어깨를 삼각측량하는 방식(stereo)이 가장 안정적이었고(위치 흔들림 약 3cm), 발목 방식(ankle1)은 빠르지만 0.3~0.5m 멀게 나왔다. 실측이 필요한 항목(렌즈·위치 보정, 세 방식의 실제 위치, 알람, 앱 자원)은 교육장에서 재고, 같은 지점 반복 비교(10-7 거리표)와 이동 타겟(10-8)은 가상 시험으로 했다.

| 단계 | 결과 | 판정 |
| --- | --- | --- |
| 10-1 렌즈 보정 | VIGI 0.727px, C920 0.169px | ✅ |
| 10-2 위치 보정 | 체커보드 방식, 칸 크기 24.1 vs 24.0mm | ✅ |
| 10-3 발목 (ankle1) | C920 단독, 오차 약 20cm | ✅ |
| 10-4 삼각측량 (stereo) | 약 2.6m 지점, 흔들림 약 3cm | ✅ |
| 10-5 보완 (fused) | 한 카메라만 보여도 추적 유지, 오차 약 10~20cm | ✅ |
| 10-6 타겟 + 알람 | 시나리오별 3회 이상 정상, 글로 타겟 찾기 성공 | ✅ |
| 10-7 결과 비교 | 거리표는 가상 시험, fps·시간 차·RAM은 실측 | ⚠️ |
| 10-8 이동 타겟 | 가상 시험: 속도 추정 ±0.01m/s, 1.5m/s에서 충돌 위험 알람이 근접 알람보다 1.0초 먼저 | — |

코드는 세 군데를 고쳤다. `camsrc.py`는 VIGI(RTSP)·다른 RTSP·USB 번호를 같은 방식으로 열고, `calib_intrinsics.py`·`calib_extrinsics.py`는 카메라 1~2대를 받는다. `proximity_app.py`는 카메라 대수에 맞춰 기본 모드를 고르고, RTSP와 USB를 섞을 때를 위해 시간 차 허용치(`--max-skew`)를 옵션으로 두었다.

### 10-1 렌즈 보정

| 카메라 | 입력 | 재투영 RMS (px) | 비고 |
| --- | --- | --- | --- |
| VIGI C540-W | RTSP stream2, 848x480 | 0.727 | 광각 렌즈라 술통형 왜곡이 큼 |
| Logitech C920 PRO | USB, 640x480 | 0.169 | 렌즈 중심·fx=fy 고정, fx 680.6 |

- C920은 왜곡이 작아 렌즈 중심이 보정할 때마다 달랐다(cy 289.9 / 356.2). 그래서 중심을 화면 가운데로, fx와 fy를 같게 고정하고 다시 보정했다.
- 고정한 만큼 RMS는 낮게 나올 수 있다. 실제 품질은 10-2의 검증(칸 크기)으로 판단했다.
- 카메라 1대였던 10/26~27에는 VIGI를 따로 보정했다(fx 817.7, fy 826.9, k1 −0.716). 노트북 화면에 체커보드(칸 24mm)를 띄웠는데, 휘어 보이는 격자를 기본 방식이 못 찾아 왜곡에 강한 SB 방식을 더하자 20장이 모였다.

### 10-2 카메라 위치 보정 (체커보드 방식)

줄자로 바닥 기준점을 재는 대신, 두 카메라에 동시에 보이는 체커보드 하나로 위치와 방향을 구했다(`calib_board.py`). 두 카메라로 삼각측량한 칸 크기가 24.1mm로 실제 24.0mm와 0.4% 차이여서, 두 카메라의 위치 계산이 서로 맞는다고 봤다.

| 항목 | 계산값 | 확인 |
| --- | --- | --- |
| 삼각측량한 칸 크기 | 24.1mm | 입력값 24.0mm (차이 0.4%) |
| 재투영 오차 VIGI / C920 | 0.97 / 0.50px | — |
| 두 카메라 간격 | 0.387m | 핸드폰 카메라로 잰 값과 약 5%(약 2cm) 차이 |
| 카메라 높이 VIGI / C920 | 0.804 / 0.978m | 핸드폰 카메라로 잰 값과 약 10%(약 8~10cm) 차이 |

*조건 — 두 카메라를 동시에 찍고 체커보드가 멈춘 프레임만 사용, 원점은 체커보드 중심 바로 아래 바닥, 입력값은 칸 24mm·체커보드 중심 높이 1.00m. 2026-11-02.*

- 과제 기준(계산 위치와 실측 차이 20cm 이내)은 넘지 않았다. 다만 줄자가 아니라 핸드폰 카메라로 잰 값이라 그 자체에도 오차가 있다.
- 과제의 검증점 C1·C2는 바닥 기준점 방식(`calib_extrinsics.py`)에서 쓰는 점이라 체커보드 방식에는 없다. 그래서 칸 크기 검증으로 대신했다.
- 칸 크기를 틀리게 넣으면 모든 거리가 같은 비율로 어긋난다. 재투영 오차는 모양만 보므로 이 실수를 잡지 못한다.

### 10-3 발목 방식 (ankle1, C920 단독)

VIGI 화면에는 바닥이 거의 안 보여 C920만 썼다(`--cams 0 --calib 1`). 발목이 보이게 서 있으면 위치 오차는 약 20cm였다.

| 항목 | 값 |
| --- | --- |
| 계산된 거리 | 카메라에서 약 2.9m |
| 실제 위치와 차이 | 약 20cm |
| 위치 흔들림 | 약 12cm |
| 처리 속도 | 약 26fps |

- 이상값: 앞으로 나오자 위치가 (4.15, 0.31)로 튀고 추적 번호가 바뀌었다. 카메라에 가까워지면 발목 점을 잘못 잡을 수 있다.
- 책상에 발이 가려지는 경우는 실측하지 않았다(10-7 가상 시험에서 확인).

### 10-4 삼각측량 (stereo)과 10-6 접근 알람

두 카메라를 모니터 위에 나란히 두고 stereo 모드로 돌렸다. 처리 속도는 18~24fps였고, 서 있는 사람의 위치가 약 3cm 안에서만 흔들렸다. 접근·이탈·경계에 서 있기·옆으로 지나가기를 각각 3회 이상 해 모두 알람이 제대로 동작했다.

| 항목 | 결과 |
| --- | --- |
| 서 있는 사람 위치 | 카메라까지 약 2.6m, 좌우 0.05m (실제 약 2~3m 지점) |
| 위치 흔들림 | 약 3cm |
| 어깨 높이 | 1.83m (턱 위에 선 상태) |
| 재투영 오차 | 6~7px |
| 근접 알람 | 동작 (0.4~0.6m에서) |
| 이탈 알람 | 동작 (1.3m에서, `--gate 1.5` 적용 후) |

*설정 — 타겟 (1.8, 0), 근접 0.5m, 해제 1.2m. 방이 좁아 문서 기본값(1m, 3m)보다 줄였다. 2026-11-02.*

- 추적 끊김: 걸을 때 위치가 튀어 추적 번호가 자주 바뀌었다. 같은 사람으로 잇는 거리(`--gate`)를 0.8m에서 1.5m로 늘리자 이탈 알람이 나왔지만, 번호가 바뀌는 문제는 남아 있다.
- 한계: VIGI는 RTSP라 영상이 늦게 도착하는데, 앱의 시간 차는 찍은 시각이 아니라 도착 시각만 비교한다. 두 카메라의 시야가 달라 상체가 한쪽 화면에서 벗어나면 사람이 끊긴다.
- 책상에 앉음 시나리오는 이날 하지 못했다(아래 11/3 재시험).

### 10-6 재시험: 글로 타겟 지정과 앉음 판정 (11/3)

타겟을 좌표 대신 글(`--target "cardboard box"`)로 주고 종이 상자를 두 카메라에 보이게 뒀다. 글로 타겟을 찾는 부분(YOLOE가 후보를 찾고 EmbeddingGemma가 다시 확인)은 동작했지만, 그사이 C920을 다른 과제에 쓰느라 떼었다 다시 달아 위치 보정이 맞지 않았다.

| 항목 | 결과 |
| --- | --- |
| 타겟 찾기 | 시작 직후 1번은 못 찾음 → \[타겟 다시 찾기\] 뒤 두 카메라 모두 찾음 (확인 점수 0.73 / 0.732, 기준 0.15) |
| 타겟 위치 | (0.15, −0.07, 0.84)m — 실제는 약 2m 앞. 재투영 오차 76.7px (11/2에는 6~7px) |
| 카메라 시간 차 | 4ms (기준 80ms 이하, 도착 시각 기준) |
| 앉음 판정 | 2초마다 남긴 상태 60개 중 59개가 한 카메라 추정이라 자세를 못 정함, 두 카메라가 맞춘 것은 1개(서 있음) |

*설정 — `--near 0.5 --far 1.2 --gate 1.5`, 2026-11-03 18:10 무렵. 카메라를 옮긴 뒤 10-2를 다시 하지 않은 상태.*

- 보정이 틀어지자 타겟이 카메라 바로 옆에 찍혔고, 같은 사람이 카메라마다 따로 잡혀 추적 번호가 29번까지 늘었다. 상자까지 거리도 0.06~6.5m로 튀었다.
- 앉음 판정은 두 카메라로 구한 높이가 있어야 해서 확인하지 못했다. 짝짓기 허용 오차를 풀면 짝은 지어지지만 높이가 틀린 값이라 판정 근거로 쓰지 않았다.
- 배운 점: 카메라를 움직이면 10-2를 다시 해야 한다. 다른 과제와 카메라를 같이 쓸 때는 10단계를 먼저 끝내는 게 좋다.

### 10-5 보완 방식 (fused, 한 카메라 추정)

한쪽 카메라에만 보이는 자리에서도 추적이 끊기지 않았다. 한 카메라만으로 추정한 위치는 실제와 약 10~20cm 차이가 났다.

| 카메라 | 실제 위치와 차이 | 위치 흔들림 |
| --- | --- | --- |
| VIGI 단독 | 약 10~20cm | 약 3cm |
| C920 단독 | 약 10~20cm | 약 17cm |

- C920 단독 추정값으로도 근접 알람이 울렸다. 이 값은 어깨 높이를 1.2m로 가정한 것이라, 알람보다는 추적을 이어 가는 용도로 보는 것이 안전하다.

### 10-7 세 방식 비교

11/3에는 카메라가 보정 때 자리에서 옮겨져, 같은 지점에 서서 세 방식을 차례로 재는 실측을 할 수 없었다. 그래서 거리표는 11/2 보정 파일(카메라 배치 그대로)에 가상의 사람을 세운 가상 시험으로, 처리 속도·시간 차·메모리는 실제 앱을 돌려 재서 비교했다.

**거리 비교 (가상 시험)** — 칸 = 200회 중앙값(±표준편차), 단위 m

| 실제 거리·자세 | ankle1 | stereo | fused |
| --- | --- | --- | --- |
| 0.5m, 서 있음 | 0.78 (±0.03) | 0.48 (±0.10) | 0.48 (±0.10) |
| 1.0m, 서 있음 | 1.32 (±0.05) | 1.04 (±0.16) | 1.04 (±0.16) |
| 2.0m, 서 있음 | 2.43 (±0.08) | 1.97 (±0.24) | 1.97 (±0.24) |
| 3.0m, 서 있음 | 3.50 (±0.11) | 2.92 (±0.37) | 2.92 (±0.37) |
| 1.0m, 책상에 앉음 | 없음 | 1.02 (±0.15) | 1.02 (±0.15) |
| 2.0m, 책상 뒤에 서 있음 | 없음 | 1.98 (±0.24) | 1.98 (±0.24) |
| VIGI에만 보임 (실제 3.01m) | 없음 | 없음 | 1.62 (±0.05) |

*가상 시험 — 11/2 보정 파일의 두 카메라에 가상의 사람(어깨 중심 서 있음 1.40m·앉음 1.00m, 발목 0.08m)을 투영하고 관절 잡음 2px를 더해 앱과 같은 계산식(`stereo.py`)으로 위치를 다시 구함. 사람은 타겟 (1.8, 0) 뒤쪽, 앉음·책상 뒤는 발목이 가려진 것으로 둠. `mode_sim.py`. 실제 관절 검출 오차·사람 짝짓기·카메라 시간 차는 들어 있지 않아 실측보다 좋게 나온다.*

**실제 앱 자원 비교 (실측)**

| 모드 | 처리 속도 (fps) | 카메라 시간 차 (ms) | 메모리 RSS (MB) |
| --- | --- | --- | --- |
| ankle1 | 29.1 | 0 (카메라 1대) | 1,303 |
| stereo | 22.6 | 17.5 | 1,361 |
| fused | 23.4 | 26.0 | 1,347 |

*측정 — 2026-11-03 19:16, `mode_bench.sh`로 모드마다 40초씩 앱을 돌려 5초마다 기록한 값의 중앙값, 메모리는 앱 프로세스 최대 RSS. 같은 시간에 다른 TensorRT 변환이 돌고 있었다.*

- **ankle1**은 흔들림은 가장 작지만 실제보다 0.3~0.5m 멀게 나왔다. 발목은 바닥에서 약 8cm 위인데 바닥(높이 0)에 있다고 보고 시선을 연장하기 때문이고, 멀수록 더 밀린다. 발이 가려지면(앉음, 책상 뒤) 아예 위치를 못 낸다.
- **stereo**는 치우침 없이 맞지만, 흔들림이 거리에 따라 ±0.10m → ±0.37m로 커졌다. 거리 오차가 거리의 제곱에 비례한다는 식과 맞는다. 앉거나 책상에 가려져도 어깨가 보이면 위치를 낸다.
- **fused**는 두 카메라에 다 보이면 stereo와 같다. 한 카메라에만 보이면 어깨 높이를 1.2m로 가정하는데, 카메라 높이(0.8m)가 어깨와 비슷해 시선이 거의 수평이라 가정이 조금만 틀려도 거리가 크게 틀린다(3.01m → 1.62m).
- 자원: 카메라 2대를 쓰는 stereo·fused는 ankle1보다 약 6fps 느리고 메모리를 약 50MB 더 썼다. 시간 차는 둘 다 허용치(80ms) 안이다. 앞선 실측(11/2 ankle1 약 26fps, stereo 18~24fps, 11/3 fused 19.8~20.8fps·시간 차 4ms)과도 비슷하다.
- 선택: 두 카메라가 모두 보는 자리는 stereo, 한쪽만 보이는 자리는 fused로 추적만 이어 가고, 알람 판단은 두 카메라 값으로 한다.

### 10-8 이동 타겟 — 가상 시험(합성 영상)

타겟이 움직이는 사람일 때는 속도와 충돌 예상 시간(TTC)을 정답과 비교해야 하는데, 교육장에서는 정확한 속도로 걸어 주기 어렵고 11/3에는 보정도 틀어져 있어 가상 카메라 2대로 했다. 추정 속도는 실제와 ±0.01m/s 안이었고, 빠르게 다가올수록 충돌 위험 알람이 더 멀리서 울렸다.

| 실제 속도 (m/s) | 추정 속도 (m/s) | 충돌 위험 알람 때 거리 (m) | 근접 알람 때 거리 (m) | 충돌 위험이 먼저 울린 시간 (s) |
| --- | --- | --- | --- | --- |
| 0.5 | 0.49 | 0.82 | 1.47 | −1.2 (늦음) |
| 1.0 | 1.00 | 1.94 | 1.47 | 0.5 |
| 1.5 | 1.49 | 2.89 | 1.39 | 1.0 |

*가상 시험(합성 영상) — 가상 카메라 2대(1280x720, 초점거리 960px, 높이 1.2m, 간격 1.0m)가 본 합성 화면에 yolo11n-pose를 실제로 돌림. 다른 사람(타겟)이 서 있는 사람에게 다가옴, 속도 = 최근 1초 위치의 직선 기울기, 충돌 위험 = 접근 속도 > 0.5m/s 이고 TTC < 2초, 근접 알람 1.5m. 2026-11-03, `vprox.py`.*

- 거리만 보는 근접 알람은 속도와 상관없이 1.4~1.5m에서 울리지만, 충돌 위험 알람은 1.5m/s에서 2.89m에서 울려 1.0초 먼저 알렸다.
- 0.5m/s처럼 천천히 다가오면 접근 속도가 기준(0.5m/s)과 거의 같아 충돌 위험이 근접보다 늦게(0.82m) 울렸다. 천천히 다가오는 대상은 근접 알람이 막아야 한다.
- 실제와의 차이: 가상 시험은 두 카메라 시간 차가 0이다. 교육장 실측에서 시간 차는 17.5~26.0ms(stereo·fused)였고, RTSP인 VIGI는 도착 시각만 비교하므로 실제 촬영 시각 차는 더 클 수 있다. 1m/s에서 80ms면 위치가 약 8cm 더 틀린다. 또 걸을 때 추적 번호가 바뀌는 문제(10-4)가 있어, 실제로는 속도를 구하기 전에 추적을 안정화해야 한다.

### 실측과 가상 시험의 구분 (10단계)

| 구분 | 단계 | 이유 |
| --- | --- | --- |
| 실측 | 10-1 렌즈 보정, 10-2 위치 보정, 10-3 ankle1, 10-4 stereo, 10-5 fused, 10-6 타겟·알람·글 타겟, 10-7 앱 fps·시간 차·메모리 | 카메라·보정·앱이 실제로 동작하는지가 기준 |
| 가상 | 10-7 같은 지점 세 방식 거리표(`mode_sim.py`), 10-8 이동 타겟(`vprox.py`) | 같은 자리·자세를 여러 번 똑같이 만들거나 속도 정답이 필요하고, 11/3에는 카메라를 옮겨 보정이 틀어져 있었음 |

가상 시험은 관절 검출 오차·사람 짝짓기·카메라 시간 차가 없거나 작아 실측보다 좋게 나온다. 그래서 방식 간 비교와 경향 확인에만 썼다.

### 카메라 설치 조정 (1대 구성 때)

- 높이: 처음엔 카메라가 책상 위(약 1m)에 있었다. 카메라 높이가 어깨(1.2m)와 비슷하면 1대 추정이 안 돼 사물함 위로 옮겼다. 렌즈 보정은 카메라를 옮겨도 그대로 쓸 수 있다.
- 방향: 옮긴 뒤 거울·회전 설정을 다시 맞추고(사물함 번호표가 정상으로 읽히는지 확인), 통로를 따라 내려다보는 가로 화면으로 고정했다. 화면을 90°/270° 돌리면 렌즈 보정을 다시 해야 한다.
- 좌표계: 통로 바닥의 테이프 표시를 원점으로, x는 통로 끝 문 쪽, y는 왼쪽(책상 쪽), z는 위쪽으로 정했다.

## 문제 해결 기록

대부분의 오류는 코드 문제가 아니라 환경(버전, 다른 프로그램, 입력 방법) 문제였다.

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| `torchaudio`가 CUDA 13.0, torch가 13.2라 import 에러 | 다른 패키지를 깔면서 짝이 안 맞는 torchaudio가 같이 설치됨 | `pip uninstall -y torchaudio` (LLM에는 불필요) |
| 영상 임베딩에서 `torchcodec` 없음, 이후 `libswscale.so.9` 없음 | Jetson 기본 FFmpeg가 기능을 줄인 버전 | `torchcodec --no-deps` 설치 + 우분투 FFmpeg 6 부품 추가 설치 |
| `ffmpeg`로 RTSP 녹화·libx264 안 됨 | Jetson FFmpeg에 네트워크와 libx264가 빠져 있음 | `imageio-ffmpeg`의 완전한 ffmpeg(`$FF`) 사용, USB 카메라는 `-f v4l2 -i /dev/video0` |
| 파이썬 코드를 터미널에 붙여 넣어 문법 에러 | bash는 파이썬 문법을 모름 | `python << 'EOF' ... EOF`로 감싸거나 파일로 저장 |
| `nano: 명령어를 찾을 수 없음` | nano 미설치 | `sudo apt install -y nano` 또는 `cat > 파일 << 'EOF'` |
| `EOF`를 쳐도 안 끝남 (`ㄷEOF`) | 키보드가 한글 상태 | 영어로 바꾸고 다시 `EOF` 입력 |
| `ModuleNotFoundError: torch` | 가상환경 밖에서 실행 | `source ~/eg2/bin/activate` 후 실행 |
| 웹 페이지는 열리는데 0.0 fps, 영상 없음 | `웹캠을 열 수 없음` (다른 앱이 카메라 사용 중) | `sudo fuser -v /dev/video0`로 확인 후 `pkill -f pose_app.py` |
| `Ctrl + C`로 앱이 안 꺼짐 | 브라우저 영상 연결이 열려 있음 | 탭을 먼저 닫거나 `Ctrl + \`, 안 되면 새 창에서 `pkill` |
| 앱이 켜진 창에 명령을 쳐도 실행 안 됨 | 이전 앱이 아직 실행 중 | 이전 앱을 끈 뒤 프롬프트가 보일 때 입력 |
| SSH `Operation timed out` | Jetson이 Tailscale에서 오프라인(회색) | Jetson 전원·네트워크 확인, USB-C 직결(`192.168.55.1`) 대안 |
| 행동 학습 `윈도가 부족함` | 지나감·힐끗 봄 구간이 짧아 검증 조각 0 | `--window 30 --val 0.3`으로 줄임 |
| YOLOE 실행 시 CLIP 자동 설치 후 경고 | 설치 직후 반영 안 됨 | 앱을 다시 실행 |

카메라·네트워크(10단계 교육장 설치) 관련:

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| IP 카메라를 학교 와이파이에 연결 못 함 | 로그인형 와이파이, 유선은 내부망 전용 | Jetson 유선 포트에 직결, NetworkManager 공유 모드 |
| Jetson 핫스팟 안 됨 | 와이파이 카드가 인터넷을 맡고 있고 유선은 인터넷이 없음 | 유선 직결로 대체 |
| RTSP 401 Unauthorized | 비밀번호를 한글 입력 상태로 침 | 영문으로 입력, 글자 수 확인 |
| 카메라 초기화 후 접속 불가 | VIGI는 비밀번호를 활성화하기 전에는 쓸 수 없음 | SSH 터널로 관리 화면을 열어 활성화 |
| 재부팅 뒤 카메라 No route to host | 카메라 주소가 바뀜(DHCP) | MAC 주소로 다시 찾아 설정 갱신, 자동 재연결 추가 |
| 학습 중 NVML assert / 메모리 부족 | 팀원 앱·컨테이너가 메모리를 많이 씀 | `free -h`로 확인 후 실행, 팀원에게 공유 |
| 영상 판정 결과 파일이 비어 있음 | 파이프 출력 버퍼가 종료 때 버려짐 | `python -u`, 종료 전 flush |

## 배운 점

가장 크게 배운 점은 **데이터의 양만큼 깨끗함이 중요하다**는 것이다. 관심 있음 녹화에서 걸어 나가는 장면만 빼자 정확도가 22%에서 100%로 올랐다.

- **환경 버전이 먼저다.** JetPack 7에서는 자료(JetPack 6 기준)와 설치 방법이 달랐고, torch 버전을 고정해야 다른 패키지가 덮어쓰지 않았다.
- **점수는 시험 문제 구성을 봐야 한다.** 검증 조각이 한 라벨에 몰리면 100%나 78.5% 같은 숫자는 의미가 없다. 라벨별 혼동 행렬이 더 정확하다.
- **규칙은 정한 기준 밖에서 틀린다.** 측면, 짧은 고개 돌림, 가려진 관절처럼 기준값이 예상하지 못한 상황에서 오판이 났다.
- **학습 모델은 배운 것만 안다.** 학습하지 않은 만세는 아는 동작 중 하나로 억지로 분류했고, 비슷한 자세(박수↔팔짱, 지나감↔힐끗 봄)는 서로 헷갈렸다.
- **녹화와 테스트 조건을 맞춰야 한다.** 앉은 자세, 거리, 손 방향이 녹화 때와 다르면 인식률이 떨어졌다.
- **진짜 성능은 실시간·낯선 사람 테스트로 본다.** 스크립트의 검증은 같은 녹화의 뒷부분이라 높게 나온다.
